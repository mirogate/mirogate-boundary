Mirogate Boundary: Testing the Data We Send to AI

A local-first text gateway, an Arabic privacy diagnostic suite, and an honest look at what a privacy filter can miss.

A local privacy model answers one important question: where does detection happen?

Two more questions deserve just as much attention: what does the detector miss, and what does the application actually send after detection?

Today we are releasing Mirogate Boundary, an experimental open-source developer tool that makes those questions testable. It combines local text detection, explicit egress policies, a deliberately narrow API proxy, and Arabic-focused evaluation cases.

It is not a guarantee that private data cannot leave your machine. That limitation is part of the design and the documentation.

How we arrived here

Abdullah Alsaidi's Maskode work brought a useful pattern into a coding-agent workflow: detect personal information locally, replace it with placeholders, and restore values locally when appropriate. It uses OpenAI's open-weight Privacy Filter.

That connected with two projects we had already published at Mirogate: our Secure AI Engineering Framework, which describes data classification and routing, and the Arabic-Native Agent Bench, which argues for testing Arabic behavior directly.

Boundary is our independent implementation of a small, executable part of that work. We are not claiming a new foundation model or the first privacy proxy. The contribution is a concrete supported-input contract, tests that observe the outgoing payload, and an evaluation surface that keeps difficult Arabic cases visible.

What the first release does

The flow is straightforward: inspect supported text locally, apply policy, then forward the transformed request to an explicitly configured endpoint.

Under the default policy, detected personal information is replaced by random opaque placeholders. Identical values in the same detected category reuse their placeholder within one request. The mapping stays in a bounded, expiring, in-memory vault.

Detected secrets block the request. Detector failures also prevent forwarding. There is no silent switch from the local model to the weaker rules-only mode.

The proxy accepts a small text-only, non-streaming subset of the chat-completions API. It scans system, developer, user and assistant text. Unknown request fields, tool calls, media and streaming are rejected. This release does not inspect arbitrary MCP traffic, PDFs, images, telemetry or applications that bypass the proxy.

Restoration is off by default. When enabled, it only restores same-request placeholders in visible assistant message content. It does not restore executable tool arguments. Restored text remains untrusted model output.

This is reversible pseudonymization, not anonymization. Context, inferred attributes and missed entities can still identify a person.

Arabic tests need more than translated examples

We included 99 synthetic cases containing 90 labelled entities and 18 entirely negative controls. They cover contextual Arabic names, mixed Arabic/English text, Western and Arabic-Indic and Persian digits, selected financial identifiers, private dates, credential-like strings, Unicode edge cases and examples that should remain unchanged.

The corpus is small, AI-authored development material. It is not held out, representative of a population, or independently human-reviewed. Persian, Urdu and Arabizi examples are edge probes, not separate language benchmarks.

Our first rules-only run had 82.26% strict entity precision and 56.67% strict entity recall. Sensitive-character coverage was 64.41%; 34 of 90 annotated entities were completely uncovered. One of the 18 negative controls produced a false positive.

Those are results for our deterministic rules on this particular corpus. They are not OpenAI Privacy Filter scores, a comparison with Maskode, or a real-world leak rate. The rules-only mode is useful for demonstrating the workflow and inspecting selected structured identifiers; it is not sufficient general-purpose privacy protection.

Exact entity matching and character coverage answer different questions. A detector can cover an email while choosing an overlong boundary, or find most of an identifier while leaving a meaningful fragment visible. We publish both measures, the case-level counts and the dataset hash in the evaluation report.

We then completed actual model-backed evaluation on a Linux CPU runner, using the same 99 cases, a pinned checkpoint and the official Viterbi decoder:

  • Privacy Filter alone: 69.62% strict precision, 61.11% strict recall, and 81.72% annotated-character coverage.
  • Hybrid rules plus Privacy Filter: 67.59% strict precision, 81.11% strict recall, and 93.11% annotated-character coverage.

The hybrid covered more annotated text on this set, with a trade-off: four of 18 negative controls were flagged, compared with three for the model alone. Seven of 81 sensitive cases remained incompletely covered, including six entirely missed entities. These results do not establish real-world privacy.

Both modes made fresh model calls for every case; there was no prediction cache. A preliminary smoke email was missed, and that observation remains in the reports. Python socket APIs were blocked during inference with zero attempted calls recorded; that check is not an operating-system network sandbox.

Our Windows development machine blocked a PyTorch DLL through Application Control before inference. We left its policy unchanged. The published model scores come from the separate Linux run, not from the Windows attempt.

Transport tests and detector accuracy are different evidence

A detector can miss a secret even when the proxy enforces every policy correctly. Conversely, an accurate detector is not enough if a client can send an uninspected attachment or an unsupported field.

Our integration tests use a local capture server to inspect the actual forwarded JSON. They check masking and local restoration, blocking before forwarding, credential separation, rejected payloads, redirects, detector failures and bounded restoration. Other tests cover Unicode offsets, expired and foreign tokens, benchmark scoring and receipt verification.

Passing those tests establishes those tested behaviors. It does not establish perfect detection, production hardening or complete network coverage.

Audit evidence has limits too

Boundary can write receipts with category counts, input length and decision. They contain no original values, transformed text or hashes of the input text. Even those counts are metadata and should be handled thoughtfully.

The receipts form a hash chain. An independently trusted saved head can reveal later logical-chain changes or truncation. Without that anchor, someone who controls the file can rewrite the whole chain. A receipt is also no proof that every application used this proxy.

Try it without sending anything to an AI provider

Clone the repository and create a virtual environment. From the checkout, install the package and run the local demonstration:

python -m pip install -e .
python examples/capture_demo.py

The demo explicitly uses rules-only detection and a local mock provider. It prints the exact transformed text the mock received and verifies an exact local round trip. It makes no external AI call.

The optional local-model path uses a pinned OpenAI Privacy Filter runtime, checkpoint, tokenizer and Viterbi decoder. Model download is an explicit setup step; request handling never downloads a model or sends text to a hosted detector. Follow the model setup instructions and evaluate your own lawful test cases before considering sensitive workloads.

The contribution we want next

We would value independently reviewed Arabic annotations, synthetic false-negative and false-positive cases, and reproduced model-backed results. Task utility, longer documents and carefully designed tool adapters need separate evaluation before broader claims.

If you maintain an AI integration, try the local capture demo and read the threat model. If you can help improve the corpus, submit an invented example with the expected span and the detector version. Please do not upload real customer records or active credentials.

For Mirogate, credibility means making the behavior inspectable, including the misses. The code, diagnostic corpus and reports are available under Apache-2.0; the upstream runtime and weights retain their own licenses.
